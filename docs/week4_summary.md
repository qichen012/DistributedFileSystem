# 第四周项目总结

## 一、本周目标
在前三周实现了文件上传、下载、多副本存储与健康检测的基础上，本周的目标是：
1. 支持 **可配置副本数**，使上传时可以灵活选择副本数量；
2. 实现 **文件删除功能**，支持删除数据库记录并清理存储节点上的数据；
3. 增加 **节点下线检测**，保证数据库中只保留活跃节点；
4. 对各个模块分别进行测试，验证功能正确性。

---

## 二、完成情况

### 1. 可配置副本数
- 在 `client/cli.py` 中增加了 `--replicas` 参数，用户可在上传时指定副本数（默认 2）。
- 修改 `controller/scheduler.py`，支持从节点列表中选择多个节点。
- 客户端上传时，每个文件块会被存储到多个不同节点，并在元数据服务中注册多条记录。

### 2. 文件删除功能
- 在存储节点（`storage_nodes/node.py`）实现了 `DELETE /delete_chunk` 接口，支持删除单个文件块。
- 在元数据服务（`metadata_server/routes/file.py`）实现了 `DELETE /delete_file/{file_id}` 接口，负责：
  1. 查找所有块对应的节点；
  2. 请求节点删除数据；
  3. 删除数据库中的文件与块信息。


### 3. 测试
- **副本数测试**：上传时指定 2 或 3 副本，验证在不同节点能找到副本数据；
- **文件删除测试**：上传文件后调用 `delete_file` 接口，确认节点文件和数据库记录被清理；
- **节点下线测试**：关闭一个节点进程，确认数据库中对应节点被移除。

---

## 三、问题与解决
- **问题 1**：CLI 原始参数设计导致 delete 命令需要无意义的 `filepath`。  
  **解决**：改用子命令模式（upload/download/delete），让各命令拥有独立参数。  

- **问题 2**：节点异常宕机时无法执行注销逻辑。  
  **解决**：通过 get_health_nodes()函数得到健康的节点

---

## 四、收获
- 学会了如何将「副本数」参数化，让系统更灵活；  
- 了解了分布式存储中「删除」不仅是数据库操作，还要协调存储节点；  
- 初步具备了维护「活跃节点列表」的能力，系统更接近真实可用的分布式存储系统；  
- 系统的可靠性和可控性进一步增强。
